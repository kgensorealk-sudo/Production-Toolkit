# Keeper persistent ZIP tasks — implementation plan

> Superseded for storage and processing: follow [keeper-local-task-plan.md](keeper-local-task-plan.md). Manuscripts and detailed evidence must remain local; the cloud bucket/worker proposals below are historical and must not be applied.

Date: 2026-10-09, Asia/Shanghai. Status: planning only; no schema, storage bucket, queue, application feature, or deployment is changed by this document.

Phase 1 read-only findings and concrete implementation contracts are recorded in [keeper-task-foundation-review.md](keeper-task-foundation-review.md). Real package inspection adds an Attach missing file workflow that creates a new revision; complete XML/ORDER/PDF trios cannot be assumed for existing ZIPs. Production queue extensions are available but not installed. Proposed numerical limits remain benchmark settings until account capacity and deployed worker tests are verified.

## Confirmed requirements

- One ZIP package represents one article task. Expected evidence: JOURNALCODE_<article-number>.xml, the corresponding .order, and _edit_report.pdf.
- Users can upload multiple ZIP tasks and select the ZIP task/article to work on, not an individual constituent file.
- Each signed-in user has a private task list. No shared task list or automatic administrator browsing of manuscripts.
- Tasks, original files, evidence, conversations, findings and revisions survive refresh, browser closure and sign-out. Supabase is the persistent source of truth; browser state and the existing 15-minute process cache are optimizations only.
- Uploaded packages are inspected automatically in the background without an AI call. User selection prioritizes preparation; AI review starts only after a user gives a task instruction or chooses a review action.
- Keep everything within Keeper's sandbox. Preserve the existing Gemini connection and application-controlled allowlisted tools. No automatic manuscript correction or query closure.

## Recommended user experience

Desktop: searchable task list on the left, selected task workspace in the centre, evidence drawer on the right. Narrow screens use a task-list page and a task-detail page with an evidence sheet. The task identifier and active evidence revision remain visible while reviewing.

Upload ZIP tasks supports multi-file selection, drag/drop, per-file progress, retry and removal of unfinished uploads. The list shows task identifier, package status, preparation status, last activity and an active-review indicator. Filter by preparing, ready, needs attention and archived. Pagination and indexed search allow growth beyond a small fixed number of task cards.

Task tabs: Overview, Work with Keeper, Evidence, History. Overview shows retained package files and issues, plus Review author responses, Inspect OPT comments, Show insertion/deletion counts and Ask Keeper. Evidence provides exact snippets and locations. History retains package revisions and previous reviews. Switching tasks does not move another task's response into the selected task.

Keep three concepts separate:

| Category | Proposed states |
|---|---|
| Package | Uploading, checking, complete, needs attention, failed |
| Evidence preparation | Queued, preparing, ready, ready with limitations, failed |
| AI review run | Queued, running, finished, finished with limitations, failed, cancelled |

None of these states establishes that production corrections were completed. Ready with limitations permits work using available evidence. Malformed XML, missing PDF and failed PDF extraction retain different explanations.

## Persistence and ownership

Use the existing Supabase Auth account UUID. Enforce ownership in database RLS, private Storage policies and server endpoints. Apply explicit authenticated grants and RLS to every exposed task table. Check both existing-row access and new-row ownership on mutations. UUID knowledge or filename agreement must never grant access.

Use a private keeper-tasks bucket. Object paths are generated by the application: <owner_uuid>/<task_uuid>/<revision_uuid>/<artifact_uuid>. Retain original filenames as metadata rather than using ZIP paths as storage destinations. Store the original ZIP, the three selected constituent files, and large derived evidence objects privately. Never issue permanent public links. Download access is authorized, with short-lived signed URLs only when needed; do not log signed URLs or manuscript text.

Privileged worker credentials stay server-side. A worker may access only the validated job's owner/task/revision scope. AI tool requests receive identifiers, never arbitrary Storage paths, URLs or filesystem paths. Inspector outputs and verified findings are worker-written; ordinary browser writes cannot forge them or change ownership/source bindings.

Proposed records:

| Table | Responsibility |
|---|---|
| keeper_tasks | Owner, article identifier/display name, active revision, archive state, timestamps |
| keeper_task_revisions | Immutable ZIP/source manifest, fingerprint, package checks and lifecycle state |
| keeper_artifacts | Revision-scoped artifact ID, role, original filename, private object key, original-byte hash and size |
| keeper_inspections | Revision, inspector version, source fingerprints, preparation state, counts, diagnostics and checkpoint |
| keeper_evidence_records | Inspection-scoped OPT/query/PDF records, source locations, exact evidence and verified response bindings |
| keeper_review_runs | Owner/task/revision/inspection, user instruction, state, provider metadata, coverage and final result |
| keeper_messages | Task conversation, evidence revision, run, role, content and creation sequence |
| keeper_jobs | Persistent preparation/review/delete job metadata, priority, attempts, lease/cancellation state and idempotency key |
| keeper_user_settings | Last selected task and presentation preferences, isolated by user |

Every child record must reference the correct owner/task/revision through enforced relationships; an owner cannot attach their row to someone else's task. Index task lists by owner/activity, child records by their parent scope, and jobs by state/priority. Verify constraints against current live schema before applying changes; local SQL files alone do not prove deployed policies.

## Upload and package validation

1. Authenticate, create a task/upload record with an idempotency key, and allocate an immutable revision/object destination.
2. Upload the ZIP directly to private Supabase Storage using resumable uploads. ZIP bytes do not pass through the existing 4 MB chat request or become base64 in a conversation. Finalize upload only after server-side object verification; a browser success flag is not sufficient.
3. Persist and enqueue package inspection. Interrupted uploads remain visible as unfinished and can be retried; do not promise that a missing local file can be resumed after browser refresh without reselecting it. Previously completed uploads are restored automatically.
4. Inspect ZIP entries with streaming/bounded extraction. Bound compressed/decompressed sizes, file count, compression ratio, processing time and nesting. Reject path traversal, absolute paths, symlinks, encrypted/unsupported archives and corrupt entries. Do not execute attachments or recursively unpack nested archives.
5. Allow an enclosing folder and additional attachments, but identify the required files by an unambiguous common article stem. Handle .XML/.ORDER case differences and real article-number lengths rather than enforcing exactly five digits. Multiple equally eligible XML/ORDER/PDF files remain a package issue; never silently pick the first.
6. Check filenames and available embedded identity independently. Preserve mismatches as diagnostics; a filename is not proof of article identity. Retain .order bytes and provide read-only viewing; define semantic extraction only after inspecting representative ORDER structures and adding fixtures.
7. Detect exact duplicate ZIP bytes per owner. Offer Open existing task or Add revision to an existing task. Matching article identifiers with changed bytes suggest a revision but never overwrite automatically. Identical packages uploaded by different users remain private independent tasks.

Expose capacity and upload errors clearly. Multiple tasks are supported without a small arbitrary count cap; storage, per-package processing and fair-use limits still apply. Determine numerical limits from representative packages and the deployed account capacities before launch. A missing required file makes the package incomplete but does not erase the task or prohibit supported XML-only questions.

## Durable preparation and review

Recommend Supabase Queues for durable delivery, with a protected Node worker to reuse the existing PDF.js/native canvas runtime. Queue messages contain job identifiers only. keeper_jobs provides user-visible state and history. The queue is not exposed for arbitrary browser consumption.

Verify queue availability, worker hosting, scheduler/dispatcher capability and cost limits before finalizing deployment configuration. A queue stores work but does not execute it: wire and test an actual authenticated dispatcher and recovery schedule. Do not rely on an unawaited promise after an HTTP response, a browser timer, or a process-local queue.

Workers claim bounded jobs, check ownership and source revision, and persist checkpoints/results before acknowledging work. Use leases, fencing/generation tokens and unique job/output keys: a duplicate delivery or expired worker cannot overwrite a later result. Reclaim expired work with bounded backoff; failed tasks remain visible and retryable. Selection raises priority for the next unstarted preparation chunk; do not terminate unrelated work halfway through a commit.

Preparation stages: validate package, retain sources, inspect XML, extract PDF pages in bounded chunks, bind query responses conservatively, persist inventory and publish readiness. Checkpoint page extraction so long PDFs need not restart from page one after every timeout. Only publish a complete inspection version atomically; partial evidence is explicitly labelled and not mixed with a previous revision. Keep existing parser/page/record limits until deliberately revised and tested.

Selecting a task restores its evidence and conversation. Run task persists the instruction and review-run record before enqueuing an AI review. One active AI review per owner is the initial recommendation, enforced server-side across tabs/devices; other users are scheduled fairly. Switching tasks or refreshing does not cancel the accepted server job. Run cancellation is explicit and checked between stages/tool calls; already consumed provider work cannot be undone.

Provider requests retain the existing allowlist, argument validation, bounded tool rounds and time budget. Change the task-backed API contract to task ID, revision ID, inspection ID, instruction and request ID. The server loads authorized evidence/history; the browser does not resend whole articles or arbitrary claimed assistant history. Large evidence remains paged/on-demand. Store results before exposing completion to the UI. During rollout retain the legacy artifact path until the task-backed flow passes parity tests.

Refreshing reloads persisted task/job state. Use bounded polling initially; optional authorized Realtime later is an optimization, not the authority for job completion. Sign-out aborts client activity, clears task-sensitive in-memory state and account-specific query caches, and prevents late responses from appearing under the next signed-in account. Stored tasks remain unchanged.

## Revisions, history and deletion

- Replacing a package creates an immutable revision. The user explicitly activates it after package checking; subsequent runs pin the revision and inspection they use.
- Old runs stay attached to their original sources. A late result for a prior revision is historical, never the active revision's current finding. Inspector upgrades create a new inspection version even for unchanged file bytes.
- Preserve original-byte fingerprints for uploaded files, alongside decoded-text representation metadata used by existing XML inspection. Citation identity includes task, revision, inspection, artifact and record, not just a qN label or filename.
- Archive is reversible and keeps files. Delete is a separate explicit action scoped to one owner/task. A durable deletion job prevents further processing, removes private Storage objects through the Storage API, deletes derived/history rows and retries partial cleanup. Database cascade deletion alone does not delete stored file objects. Show Deleting until cleanup is confirmed.
- Clean up abandoned temporary uploads separately; completed tasks do not disappear because a cache TTL or routine cleanup expires. Clarify backup retention in the final deletion policy.
- Do not attach existing unscoped localStorage chat history to arbitrary new tasks. Offer explicit import of the currently available workspace when appropriate; unavailable old uploads cannot be reconstructed.

## Traceable answers and coverage

Implement after task/revision isolation works. Start with query-response reviews, then extend to OPT findings. Each finding separates observed fact, interpretation, suggested action and limitation. Evidence pointers identify current authorized records and exact quote/location. Application code validates task/revision/inspection membership, retrieval in this run, and quoted text before rendering. One bounded repair attempt is allowed; otherwise return deterministic evidence. Valid citations do not guarantee the interpretation is correct.

An evidence drawer retrieves exact XML snippets and PDF page context without changing tasks. File previews need the same access checks as downloads. Findings using historical evidence clearly identify that revision.

Calculate coverage in application code for the selected review run: relevant inventory count, fully retrieved records, partial records/continuations, verified response matches, unresolved/ambiguous/conflicting associations, inspection limits and omissions. Separate preparation coverage from review retrieval. Never merge several partial runs into a claim that one run reviewed everything. Never label retrieval or response matching as confirmed amendment completion.

## Implementation sequence and acceptance gates

1. Baseline and deployment check: preserve/review the pending Keeper bug fixes separately; inspect live Supabase schema/policies/buckets and hosting capabilities read-only; inspect ORDER samples; choose and document numerical limits and worker scheduling. No unrelated tool changes.
2. Persistence/security foundation: additive task/revision/artifact schemas, private bucket and policies, account-scoped list/detail APIs. Gate: owner A can restore their own task after refresh/sign-out and owner B cannot discover or access it through database, API or Storage.
3. ZIP intake and durable preparation: resumable uploads, validation, duplicate handling, queue/worker, checkpoints and retry UI. Gate: multiple real-sized packages prepare with the browser closed; crashes/repeated delivery cannot duplicate tasks or publish mixed/incomplete evidence as complete.
4. Task workspace and Keeper integration: list/search/filter, selection, tabs, pinned conversations/reviews, one active review per owner, restored state and safe switching. Gate: results return to the correct task/revision after refresh, switching, concurrent tabs and delayed responses.
5. Traceability and coverage: structured findings, citation validation, evidence drawer and run-specific coverage. Gate: invalid/foreign/stale/unretrieved references are rejected, partial retrieval is disclosed, and “Done” never proves implementation.
6. Lifecycle and rollout: archive/export/delete cleanup, quota feedback, recovery monitoring, deployment verification and legacy-path retirement only after parity. Gate: test account end-to-end workflow and cross-user isolation pass against the deployed configuration.

## Verification matrix

- Two independent user accounts plus a signed-out caller: CRUD, guessed IDs, owner changes, child-parent mismatches, direct Data API access, Storage listing/download/upload/delete and worker endpoint access. App-level admin role does not automatically grant manuscript access.
- Refresh/new device/sign-out/sign-in; sign out A then sign in B in the same browser; late requests must not leak previous-account state. Preserve tasks through all these transitions.
- Valid ZIP, missing members, case variants, real five/six-digit article numbers, nested folder, duplicate eligible files, extras, mismatch, corruption, encryption, traversal, symlink and decompression-limit fixtures.
- Interrupted upload, duplicate finalization, orphaned partial upload, queue redelivery, worker crash, lease expiry, stale worker result, queue priority, cancellation and fairness. Provider timeout/retry must not silently create duplicate billed reviews; ambiguous provider completion is recorded honestly.
- Actual XML/PDF extraction parity, strict DOI/unique-query/QID/wording/answer checks, font runs, proof callouts, OPT spaces/nesting/empty tags, caps and malformed XML. Keep real manuscripts out of portable fixtures and Git.
- Persisted paged evidence, long continuations, citations with altered quotes or foreign revision IDs, forged client coverage, partial whole-query/OPT requests and deterministic fallback.
- Concurrent revision activation and deletion during work; object cleanup retries; no resurrection by delayed workers. No default automatic manuscript edits or case closure.
- Meaningful component tests, API/database/storage integration tests, TypeScript, production build and authenticated deployed browser verification. No DTD/VTool claims for this task-management feature.
